## M6 Linux Flatpak/tray research (2026-10-02)

- Local filesystem inspection verified a native Linux Steam installation at `~/.local/share/Steam`, app `799960`, with the live `Bin/WizardClient.log` at `steamapps/common/Wizard101/Bin/WizardClient.log`. The `.steam/steam` and `.steam/root` symlinks resolve to that root. No log was found under the app's `compatdata/799960`, and no Proton game process was running; do not label the observed file a Proton session. The Flatpak Steam data roots below `~/.var/app/com.valvesoftware.Steam` were researched in the [Flathub Steam manifest](https://github.com/flathub/com.valvesoftware.Steam/blob/beta/com.valvesoftware.Steam.yml) but are not installed or verified on this host.
- [Flatpak sandbox documentation](https://docs.flatpak.org/en/latest/sandbox-permissions.html) describes restricted host file access and recommends narrow filesystem permissions. The manifest therefore has read-only mounts for the native Steam roots and candidate Steam Flatpak roots. Static permissions cannot include arbitrary secondary libraries safely, so the app asks the user to select one folder through the [XDG FileChooser portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.FileChooser.html). The portal grant/path is persisted in a separate, versioned app-data registry and revalidated against the Wizard101 Steam app manifest. No host/home-wide permission is granted.
- `discord-rich-presence` 1.1.0's [Unix IPC implementation](https://docs.rs/discord-rich-presence/latest/src/discord_rich_presence/ipc_unix.rs.html) checks the Flatpak Discord socket under `$XDG_RUNTIME_DIR/app/com.discordapp.Discord/discord-ipc-*` and native IPC under `$XDG_RUNTIME_DIR/discord-ipc-*`. Flathub's [Discord wrapper](https://github.com/flathub/com.discordapp.Discord/blob/master/discord.sh) uses the app-scoped socket location. To limit host runtime visibility, this manifest grants that specific app directory and native socket index 0 only. Other native socket indices and whether an exact permission follows a replaced socket require live validation.
- `ksni` 0.3.6's [API/docs](https://docs.rs/ksni/0.3.6/ksni/) expose the StatusNotifierItem protocol, blocking service, and Flatpak no-well-known-name behavior. `tray-icon` 0.24.2 from Tauri is a viable cross-platform alternative, but its standard Linux backend brings GTK/AppIndicator/libxdo dependencies. A platform-neutral `tray` module contains the Linux adapter so Windows/macOS implementations can be added separately. `ashpd` 0.12.3 is used for the folder portal.
- The [Flathub runtime guide](https://docs.flathub.org/docs/for-app-authors/runtimes) and current [Freedesktop Platform listing](https://flathub.org/en/apps/org.freedesktop.Platform) show runtime/SDK 26.08 available at this milestone date. Rust packaging follows the official [flatpak-cargo-generator](https://github.com/flatpak/flatpak-builder-tools/tree/master/cargo) archive/checksum/inline Cargo configuration format. `packaging/flatpak/cargo-sources.json` was generated from the committed Cargo.lock and contains only registry sources; the build is offline and lockfile-pinned.
- This host has Flatpak 1.18.3 but not `flatpak-builder`; it has no Steam Flatpak, active Proton session, or Discord Flatpak to validate permissions against. Static compilation and logic tests do not prove these package/runtime behaviors.

### M7 startup replay and restart timer policy (2026-10-02)

- The owner reports packaged Windows startup/tray/Steam/Discord and Stone Town presence passed, but restarting the app in the same zone did not restore presence until a fresh zone event. This is a concrete current M7 regression.
- Existing behavior opens `WizardClient.log` at end-of-file and starts with an empty `GameState`; therefore no initial zone record is observed after a restart while stationary.
- Startup restoration will stream the captured existing file prefix through the ordinary parser/state transitions after opening the tailer at the prefix's end offset. This preserves append continuity and avoids loading the entire log into memory. Selection and unknown-zone events are replayed in sequence; only a final verified catalog mapping creates readable presence. The log is scanned once per watcher startup; appended tailing remains incremental.
- The location timer intentionally resets at application startup on restoration. Existing verified log data does not justify translating older log times to a stable wall-clock entered-at timestamp across restarts.
- WizRust101-DB was inspected as the preferred name source; the exact Stone Town candidate agrees with the existing verified row. No additional mappings were promoted, and unknown zones remain unresolved.

### M8 native macOS and CrossOver research (2026-10-04)

- M8 is a native macOS application beginning with Apple Silicon and macOS 15+. CrossOver hosts the Windows Steam/Wizard101 client only; WizRust101-RPC must be a native macOS process.
- CodeWeavers documents `~/Library/Application Support/CrossOver/Bottles` as the default private bottle directory, configurable with its per-user `BottleDir` preference or `CX_BOTTLE_PATH`. CrossOver 24+ exposes bottle-folder changes in Settings. Published bottles may be in `/Library/Application Support/CrossOver/Bottles` or configured managed directories. A user can also put a bottle folder on an external volume. The app will inspect defaults and preferences without requiring terminal setup and provide a native folder picker for additional bottle roots. It will not assume the RPC inherits CrossOver environment variables.
- CodeWeavers documents that each bottle contains a C: drive and Windows applications. Steam inside CrossOver therefore supplies the authoritative `libraryfolders.vdf` and `appmanifest_799960.acf`; drive-letter library paths must be translated with that bottle's `dosdevices` mappings before resolving the manifest's install directory and `Bin/WizardClient.log`. This algorithm is implementable without guessing a host path, but it is not yet live-verified against a macOS Wizard101 installation. The exact log existence/permissions and library layout remain M8 acceptance questions.
- Discord's RPC documentation specifies Unix-domain socket search locations on macOS: `XDG_RUNTIME_DIR`, `TMPDIR`, `TMP`, `TEMP`, and `/tmp`, trying `discord-ipc-0` through `discord-ipc-9`. `discord-rich-presence` 1.1.0 uses a Unix stream transport and this search scheme; reuse the existing transport/retry logic.
- `tray-icon` 0.26.0 supports a macOS status item and states its event loop/status item must be created on the main thread. Use the existing winit event-loop architecture in a dedicated macOS adapter. Set accessory/agent app behavior so no Dock icon or window appears.
- Apple documents `LSUIElement` for an agent app hidden from the Dock. Direct distribution requires Developer ID signing; Apple's notarization guidance requires signed executable code and hardened runtime. A `.app` bundle is the native structure, with `.pkg` an option to install it into `/Applications`; the user app identifier and icon must be included. Local unsigned app builds can test integration before signing. No App Sandbox or unrelated TCC entitlement is planned; folder selection is the explicit authorization path for nonstandard roots.
- Apple supports both `arm64` and `x86_64` macOS targets and documents Universal binaries combined with `lipo`. Rust and the project dependencies are multi-target, so Universal 2 is technically plausible. It requires successful native dependency builds and tests on both architectures. M8 gates Apple Silicon first; Intel/macOS 15 and Universal 2 remain conditional on current CrossOver compatibility and native test evidence.

Primary sources: [CodeWeavers bottle directory settings](https://support.codeweavers.com/en_US/change-the-bottle-directory-in-crossover), [CodeWeavers CrossOver user guide](https://support.codeweavers.com/crossover-mac-user-guide?kb_language=en_US), [CodeWeavers Steam installation guide](https://support.codeweavers.com/installing-steam-in-crossover?kb_language=en_US), [Discord IPC documentation](https://discord.com/developers/docs/topics/rpc), [`tray-icon` project documentation](https://github.com/tauri-apps/tray-icon), [CrossOver current system requirements](https://www.codeweavers.com/crossover/), [Apple Universal binary guide](https://developer.apple.com/documentation/apple-silicon/building-a-universal-macos-binary), [Apple LSUIElement](https://developer.apple.com/documentation/bundleresources/information-property-list/lsuielement), [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), and [Apple package distribution](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

- WizRust101-DB remains canonical/preferred for location display-name candidates. Its confidence diagnostics must be respected; it does not establish a zone's world. No mappings were added during M8 planning.

## Discord

- [Discord RPC documentation](https://discord.com/developers/docs/topics/rpc): Rich Presence can be set over IPC to a running local Discord client. The IPC transport supports Windows named pipes (`\\?\pipe\discord-ipc-{n}`) and command `SET_ACTIVITY`. Current docs recommend Discord Social SDK for new integrations embedded in games; this project is a companion application, so a local IPC client crate is the matching implementation shape to evaluate.
- [Discord Rich Presence overview](https://discord.com/developers/docs/rich-presence/overview): activities support text, timestamps, and uploaded art assets. Discord displays the registered application name as the title; asset keys must refer to application assets.
- [Discord RPC source repository](https://github.com/discord/discord-rpc): documents connection, reconnection, and protocol handling tradeoffs for direct IPC implementations.

## Rust IPC candidates

- [`discord-rich-presence` on docs.rs](https://docs.rs/discord-rich-presence/latest/discord_rich_presence/): documented synchronous Rust API over Discord IPC with Windows and Unix implementations; supports connecting and `set_activity`.
- [`presenceforge` on docs.rs](https://docs.rs/presenceforge/latest/presenceforge/): documented Windows named-pipe and Unix socket transport, sync/async APIs, activity builder, and clear activity. Newer candidate with a larger runtime/API surface.
- Decision: no crate is selected in this spec-only milestone. Select one during the IPC implementation milestone after reviewing source/release history, license, compatibility, and integration testability. Do not implement raw Discord IPC unless candidate review establishes a concrete need.
